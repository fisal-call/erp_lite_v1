# ERP Lite — Frontend Implementation Specification (Phase 4)
### مواصفة تحضيرية فقط — بدون تنفيذ. جاهزة يعمل عليها Aider/DeepSeek مباشرة على الـ API الفعلي المبني.

**التقنية المقترحة:** React 18 + TypeScript + React Router + TanStack Query (للاتصال بالـ API) + shadcn/ui أو Ant Design (عربي RTL جاهز) + react-hook-form + Zod.
**اللغة:** عربي RTL بالكامل، مع دعم إنجليزي لاحقاً (المعمارية جاهزة له من `system.doc_field_translation` وقت الحاجة).

---

## 1. البنية العامة (Navigation)

```
تسجيل الدخول (بدون Sidebar)
└── بعد الدخول: Layout ثابت
    ├── Sidebar (يمين الشاشة لأن RTL): روابط الموديولات
    ├── Header: اسم الشركة/الفرع الحالي + اسم المستخدم + زر خروج
    └── منطقة المحتوى: الشاشة الحالية
```

### روابط الـ Sidebar (بالترتيب المتوقَّع للاستخدام اليومي)
1. لوحة المتابعة (Dashboard)
2. المبيعات (عملاء، عروض أسعار، أوامر بيع، فواتير، مرتجعات)
3. المشتريات (موردين، أوامر شراء، فواتير موردين)
4. المخزون (أصناف، مخازن، رصيد المخزون)
5. المحاسبة (شجرة الحسابات، القيود، ميزان المراجعة)
6. الإعدادات (المستخدمين، الشركة، الفروع)

---

## 2. لوحة المتابعة (Dashboard)

**المصدر:** `GET /api/v1/inventory/stock-balance` + استعلامات مباشرة لاحقة على `reporting.v_customer_outstanding`/`v_supplier_outstanding`/`v_trial_balance` (تحتاج Endpoints جديدة بسيطة في `core_org` أو `reporting` — غير موجودة بعد، أضفها كـ `GET /api/v1/reporting/dashboard-summary` أول حاجة تُبنى في الباك إند لو الوقت سمح).

**البطاقات (Cards) في أعلى الشاشة:**
| البطاقة | المصدر |
|---|---|
| إجمالي المبيعات هذا الشهر | مجموع `sales_invoice.total_amount` بحالة `submitted`+ |
| إجمالي المشتريات هذا الشهر | نفس المنطق لـ `purchase_invoice` |
| ذمم مدينة (عملاء) | `reporting.v_customer_outstanding` مجموع `balance_due` |
| ذمم دائنة (موردين) | `reporting.v_supplier_outstanding` مجموع `balance_due` |

**جدول أسفل الشاشة:** آخر 10 أوامر بيع + آخر 10 أوامر شراء (تبويبين Tab).

## 3. المبيعات (Sales Module)

### 3.1 شاشة العملاء (`/sales/customers`)
- **قائمة (List View):** جدول — الكود، الاسم، الهاتف، الرصيد المستحق (من `v_customer_outstanding`)، الحالة (نشط/موقوف)، أزرار (عرض/تعديل).
- **البحث:** حقل بحث فوري (Debounced 300ms) على الاسم والكود.
- **الفلاتر:** حالة (نشط/موقوف)، نطاق رصيد مستحق.
- **زر "عميل جديد"** يفتح نموذج (Modal أو صفحة منفصلة).

### 3.2 نموذج إنشاء/تعديل عميل
| الحقل | النوع | ملاحظات |
|---|---|---|
| كود العميل | نص، إلزامي | يُعرض تحذير لو مكرر (من رد الـ API 422) |
| اسم العميل | نص، إلزامي | |
| الهاتف | نص | |
| البريد الإلكتروني | Email | |
| حد الائتمان | رقم عشري | اختياري |

**عند التعديل:** الحقل `expected_version_no` يُرسَل تلقائياً (مخفي عن المستخدم) من قيمة `version_no` المعروضة في آخر تحميل — **لو ظهر خطأ 409 (تعارض تعديل)**، تُعرض رسالة: "تم تعديل هذا السجل من مستخدم آخر، جاري إعادة التحميل" ويُعاد جلب البيانات تلقائياً.

### 3.3 شاشة أوامر البيع (`/sales/orders`)
- **قائمة:** رقم المستند، العميل، التاريخ، الحالة (شارة ملوّنة: مسودة=رمادي، معتمد=أخضر، ملغى=أحمر)، الإجمالي.
- **فلاتر:** الحالة، نطاق تاريخ، العميل.
- **زر "أمر بيع جديد"**

### 3.4 نموذج أمر بيع جديد (أهم شاشة في النظام — أعقد نموذج)
**تخطيط الشاشة:**
```
[اختيار العميل — Autocomplete بحث حي]     [التاريخ]     [العملة]
──────────────────────────────────────────────────────────
جدول البنود (قابل للإضافة/الحذف ديناميكياً):
| الصنف (بحث Autocomplete) | الكمية | السعر | الإجمالي | حذف |
[+ إضافة بند]
──────────────────────────────────────────────────────────
الإجمالي الكلي: XXX ج.م
[حفظ كمسودة]  [حفظ واعتماد]
```
- **بحث الصنف:** Autocomplete يستدعي `GET /api/v1/inventory/items?search=...` (يحتاج إضافة `search` param للـ Endpoint الحالي — غير موجود بعد، أولوية عالية).
- **التحقق قبل الإرسال:** لا يقل عدد البنود عن 1 (رسالة عربية واضحة لو حاول يحفظ فاضي).
- **زر "حفظ واعتماد":** يستدعي `POST /sales-orders` ثم فوراً `POST /sales-orders/{uuid}/submit` — لو فشل الاعتماد (لأي BR)، يبقى المستند محفوظاً كمسودة وتُعرض رسالة الخطأ بوضوح (مثال: "العميل موقوف" لـ BR-SAL-009).

### 3.5 شاشة عرض أمر بيع (تفاصيل)
- كل بيانات الأمر + جدول البنود (قراءة فقط).
- **زر "اعتماد"** يظهر فقط لو الحالة `draft`.
- **شارة الحالة** واضحة بالألوان.
- **سجل بسيط:** "أُنشئ بواسطة [الاسم] في [التاريخ]" (يحتاج endpoint يرجّع اسم منشئ المستند من `created_by` — حالياً بيرجّع ID فقط، يحتاج JOIN بسيط في الـ Backend).

*(نفس النمط بالضبط لباقي وحدات المبيعات: عروض أسعار، تسليمات، فواتير، مرتجعات — لم تُبنَ في الـ Backend بعد الأربعة دول، فالواجهة تُبنى بعد اكتمالهم بنفس القالب.)*

## 4. المشتريات (Purchasing Module)

**نفس القوالب بالضبط من قسم المبيعات، بتبديل:**
- عميل → مورد (`/purchasing/suppliers`)
- أمر بيع → أمر شراء (`/purchasing/purchase-orders`)
- BR-SAL-009 (عميل موقوف) → BR-PUR-010 (مورد Blacklisted)

## 5. المخزون (Inventory Module)

### 5.1 شاشة الأصناف (`/inventory/items`)
- قائمة + بحث + فلتر بالفئة.
- نموذج إنشاء: الكود، الاسم، الفئة (Dropdown من `item-categories`)، وحدة القياس (Dropdown).

### 5.2 شاشة رصيد المخزون (`/inventory/stock-balance`)
- جدول من `GET /inventory/stock-balance` مباشرة: الصنف، المخزن، الكمية المتاحة.
- **تنبيه بصري (أيقونة حمراء)** لو الكمية = 0 أو سالبة.
- فلتر بالمخزن.

### 5.3 شاشة المخازن (`/inventory/warehouses`)
- قائمة بسيطة + نموذج إنشاء (الاسم، السماح بالسالب Checkbox — BD-001).

---

## 6. المحاسبة (Accounting Module)

### 6.1 شجرة الحسابات (`/accounting/accounts`)
- **عرض شجري (Tree View)** وليس جدول عادي — الحسابات الرئيسية (`is_group=true`) قابلة للطي/الفتح.
- نموذج إنشاء: الكود، الاسم، النوع (Dropdown: أصول/خصوم/حقوق ملكية/إيرادات/مصروفات)، حساب رئيسي؟ (Checkbox).

### 6.2 القيود اليومية (`/accounting/journal-entries`)
**نموذج إنشاء قيد (شاشة متخصصة):**
```
التاريخ: [___]     البيان: [_______________]
────────────────────────────────────────
| الحساب (بحث) | مدين | دائن |
[+ سطر جديد]
────────────────────────────────────────
مجموع المدين: XXX     مجموع الدائن: XXX     [متوازن ✓ / غير متوازن ✗]
[حفظ]
```
- **تحقق فوري في الواجهة (قبل الإرسال):** مجموع المدين = مجموع الدائن، وإلا زر الحفظ معطَّل ويظهر الفرق بالأحمر.
- **بعد الاعتماد (`submit`)، لا يوجد أي زر "تعديل" على الإطلاق** — يطابق BR-ACC-001 (لا Endpoint تعديل موجود أصلاً في الباك إند، فالواجهة تعكس هذا بعدم إظهار الخيار، وليس فقط تعطيله).

### 6.3 ميزان المراجعة (`/accounting/trial-balance`)
- جدول من `reporting.v_trial_balance` (يحتاج Endpoint جديد بسيط `GET /api/v1/accounting/trial-balance`).
- أعمدة: كود الحساب، اسم الحساب، مدين، دائن، الرصيد الصافي.

## 7. الإعدادات (Settings)

### 7.1 المستخدمون (`/settings/users`)
- قائمة + نموذج إنشاء مستخدم جديد (يستدعي `POST /security/users` — **يحتاج حماية Admin أولاً قبل نشر هذه الشاشة للعامة**، راجع "أولوية 2" في دليل التشغيل).

### 7.2 الشركة/الفروع (`/settings/company`)
- عرض بيانات الشركة الحالية (قراءة فقط في هذه المرحلة — لا Endpoint تعديل بعد).

## 8. الصلاحيات (Permissions) — تطبيق في الواجهة

| القاعدة | التطبيق |
|---|---|
| لا Endpoint حالياً يفرّق بين الأدوار فعلياً (كل مستخدم مصادَق عليه يقدر يعمل كل حاجة) | الواجهة **لا تُخفي** أزرار حسب دور وهمي غير موجود في الباك إند فعلياً — إخفاء زر بدون حماية فعلية في الـ API خداع أمني، مش حماية حقيقية |
| **التوصية:** لو محتاج فرق أدوار فعلي (مثلاً أمين مخزن ميقدرش يشوف المحاسبة)، ده لازم يُبنى الأول في الباك إند (`security.permission_rule` موجود في الـ DB لكن مش متفعّل في أي Endpoint لسه) — **فجوة موثَّقة، أولوية متوسطة** |

---

## 9. التصدير والطباعة

| الميزة | الحالة |
|---|---|
| تصدير Excel | يُبنى في الواجهة بمكتبة `xlsx`/`sheetjs` من بيانات الجدول المعروض مباشرة (Client-side) — لا حاجة لـ Backend endpoint خاص |
| تصدير PDF لمستند (فاتورة/أمر) | يحتاج قالب طباعة مخصص لكل نوع مستند (`react-to-print` أو توليد PDF بمكتبة `@react-pdf/renderer`) — **يُبنى بعد استقرار الشاشات الأساسية، ليس أولوية أولى** |
| الطباعة الحرارية (لو المعرض محتاج فواتير كاش سريعة) | غير مذكورة في المتطلبات الأصلية — **سؤال مفتوح لازم يتحسم قبل البناء لو مطلوبة فعلاً** |

---

## 10. ترتيب البناء المقترح (Aider/DeepSeek يتبعوه بالترتيب)

1. **البنية الأساسية:** Login screen + Layout + Sidebar + Auth Context (تخزين الـ Token، تجديد تلقائي عند 401).
2. **المبيعات كاملة** (العملاء + أوامر البيع) — لأن الباك إند بتاعها الأكمل والأكتر اختباراً.
3. **المشتريات** (نفس القالب حرفياً).
4. **المخزون** (الأصناف + رصيد المخزون).
5. **المحاسبة** (شجرة الحسابات + القيود).
6. **لوحة المتابعة** (آخر حاجة، لأنها بتحتاج بيانات من كل الموديولات التانية أول ما تتبني).

---

## 11. فجوات في الـ Backend لازم تتسد أثناء بناء الواجهة (مش بعده)

| الفجوة | التأثير على الواجهة |
|---|---|
| `GET /inventory/items` بدون `?search=` param | البحث الحي عن الأصناف في نماذج البيع/الشراء مش هيشتغل من غير ده |
| مفيش Endpoint لاسم منشئ المستند (بيرجّع ID فقط) | شاشة تفاصيل المستند مش هتقدر تعرض "أُنشئ بواسطة [اسم]" |
| مفيش `GET /accounting/trial-balance` ولا `GET /reporting/dashboard-summary` | شاشتين (6.3 واللوحة) مش هيشتغلوا من غيرهم |
| `security.permission_rule` مش متفعّل في أي Endpoint | مفيش فرق أدوار حقيقي ممكن يتطبق في الواجهة |

**التوصية:** الأربعة فجوات دول صغيرة (كل واحدة Endpoint واحد بسيط) — يُفضَّل تُضاف للباك إند بالتوازي مع بناء الواجهة، مش قبله بالكامل.
